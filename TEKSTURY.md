# Текстура по размеру браша (v127)

## Что было не так

На все грани шёл один и тот же скейл `UVS=8` и нулевое смещение. Значит рисунок
лежал сеткой мира, а край браша резал его где придётся:

* ящик 96u при повторе 96u — повезло, если начало повтора совпало с ребром; чаще
  на ящике видно правый край одной картинки и левый край следующей;
* стена 736u — семь повторов и обрубок;
* поднятый на 40u ящик — рисунок сдвинут по вертикали на 40u относительно ребра.

## Что делает подгонка

На каждую грань считается **свой** скейл, чтобы вдоль неё уложилось **целое**
число повторов, и **своё** смещение, чтобы шов сел **ровно на ребро** браша.

Формат VMF:

```
"uaxis" "[ux uy uz uoffset] uscale"
тексель = (точка · ось) / uscale + uoffset
```

Отсюда всё остальное:

| величина | формула | почему |
|---|---|---|
| текселей в повторе | `TEXW = unit / UVS` | по определению `unit`: столько юнитов занимает повтор при скейле `UVS` |
| скейл для периода `P` | `UVS · P / unit` | период = `uscale · TEXW` |
| скейл для `n` повторов на длину `L` | `L · UVS / (unit · n)` | подставили `P = L/n` |
| смещение | `-c0 / uscale` | тексель обнуляется при `точка·ось = -uoffset·uscale`, надо `= c0` |

Смещение **не сворачивается** по модулю периода. Свёртка держала бы числа
маленькими, но верна только пока `unit` угадан правильно. Без неё точка старта
текстуры садится на ребро при ЛЮБОМ размере текстуры, а ошибка в `unit` портит
лишь число повторов.

`c0` — минимум проекции точек грани на ось. Для оси `-Y` это `-y1`, для `-Z` это `-z1`.
Приближений нет: обе формулы точные.

## Первая редакция не сработала. Почему

Одна величина `tile` делала два разных дела: задавала, КАКОГО РАЗМЕРА хочется
видеть рисунок, и служила физической опорой «сколько юнитов занимает повтор при
скейле UVS». Это разные числа, и от их смешения подгонка самоуничтожилась:

```
повторов = L/tile        скейл = L·UVS/(tile·повторов)   ->   скейл ≈ UVS
```

`tile` сокращался, скейл всегда выходил равным опорному — ровно тем, что было
до всей работы. Менялось только смещение, и в игре не менялось ничего. Никакое
положение ползунка это исправить не могло: обе роли двигались вместе.

## Замер вместо догадки

Физическую опору дал файл `yashiki.vmap` — два ящика, собранных руками в
Hammer 2 на материале `cs_italy/picrate1`:

| куб | textureScale | смещение | повторов на грань |
|---|---|---|---|
| 32u | 0.125 | по Y 128 текселей | ровно 1 |
| 16u | 0.0625 | нули | ровно 1 |

Проверка по `texcoord`: 1440/32 = 45, 1472/32 = 46 — ровно один шаг. Отсюда:

* скейл Source 2 — это **юнитов на тексель**; `picrate1` = 256 текселей,
  значит при 0.125 повтор занимает 256·0.125 = **32 юнита**;
* импортёр **делит скейл VMF на 64 и умножает смещение на 64**
  (VMF 2 → Source 2 128 — сходится на первом ящике).

`tools/uvref.js` воспроизводит оба ящика по формуле экспорта до последней цифры.
Это единственная ground truth по текстурам: CS2 из этой среды не запустить.

## Ручки

`const V127 = { fit:true, unit:32, want:96, snap:1.35, all:false }`

* **`unit`** — сколько юнитов занимает повтор при опорном скейле `UVS`. 32 по
  замеру. Это **свойство материала**: у текстуры вдвое большего разрешения число
  вдвое больше. Ползунок «Натуральный размер текстуры, юнитов». Если в игре
  рисунок выходит вдвое мельче или крупнее ожидаемого — крутить надо ЭТУ ручку.
* **`want`** — какого размера хочется видеть один повтор, условно «какой ширины
  один ящик». Влияет **только** на выбор числа повторов, на скейл не влияет.
  96 — размер ящика на реальных картах. Ползунок «Размер рисунка (один ящик)».
* **`snap`** — насколько можно тянуть повтор, чтобы попасть в целое число.
  1.35 = максимум в 1.35 раза или в 1/1.35, дальше берётся соседнее число повторов.
* **`all`** — подгонять и пол со стенами. **По умолчанию выключено**: пол и стены
  нарезаны жадным мешером на плиты произвольного размера, у каждой вышел бы свой
  период, и рисунок разъехался бы на каждом стыке. Тело — другое дело: это
  ПРЕДМЕТ, у него есть свои рёбра, и текстура обязана кончаться на них.

Грань короче половины натурального повтора (16u) не подгоняется: это обвязка,
карниз, шов. Целый повтор туда пришлось бы сжать больше чем вдвое.

## Где подгонка включена

Аргументом `fitN` у `box` / `rboxZ` / `wedgeX` / `wedgeY`:
`0` — сетка мира, `'a'` — сколько целых повторов влезет, число — ровно столько повторов.

Сейчас `'a'` стоит на укрытиях (включая перегородки до потолка и их карнизы) и на
всех предметах мест — колонна, тумба, бочки, штабель, стенка, контейнер, навес, помост.

## Вычитание и куски

`resolveREG` режет коробку на куски. Куски **наследуют оси и смещения целой
коробки** — иначе на разрезе рисунок прыгнет. Поэтому у куска вдоль грани лежит
НЕЦЕЛОЕ число повторов, и это правильно.

Отсюда правило замера: **проверять подгонку по кускам из .vmf нельзя** — это два
разных прибора. Проверка живёт там же, где задана подгонка: по списку коробок `REG`.

## Повёрнутые коробки

У `rboxZ` грани повёрнуты, а оси UV были мировые: текстура ложилась наискось и
ломалась на стыке двух граней. Теперь оси собственные, вдоль рёбер. Проекция
раскладывается на постоянную и локальную координату:

```
p · (cos, sin, 0) = (cx·cos + cy·sin) + (x - cx)
```

то есть `c0` берётся сразу, без перебора углов.

## Чем проверять

```
node tools/uvref.js                                     # сверка с ящиками из Hammer
node tools/uvchk.js builds/izohrona_v120.html 3 96 32
```
Обходит `REG`, для каждой коробки считает число повторов и положение шва.
Норма: `дробных_повторов 0`, `шов_мимо 0`. Печатает гистограмму — во сколько раз
повтор крупнее натурального (при want 96 и unit 32 это около трёх).

```
node tools/uvrun.js builds/izohrona_v120.html 1 96 32   # выгружает пару fit/grid
node tools/uvpic.js /tmp/uv/<сид>_fit.vmf /tmp/uv/<сид>_grid.vmf /tmp/uvpic.png 32
```
Рисует одну и ту же грань дважды — с сеткой и с подгонкой, по настоящим осям из
файла. Это то, что видно глазом, без запуска CS2.

```
python3 tools/uvfit.py <файл.vmf> 32 8
```
Разбор готового .vmf, вспомогательный. Куски, обрезанные с дальнего края,
сохраняют ближний угол и от целых коробок неотличимы, поэтому дробные повторы
здесь ожидаемы и дефектом не являются. Точный ответ даёт `uvchk.js`.

## Что гарантированно не сломалось

Экспорт с подгонкой и без даёт **побайтно одинаковые** плоскости и материалы —
меняются только `uaxis`/`vaxis`. Проверено сравнением двух выгрузок одного сида.
Геометрия, коллизия, баланс, нав не затронуты.
