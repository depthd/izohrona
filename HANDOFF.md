# Горячие точки на картах «Изохроны»

## Цель

Пользователь подтвердил, что «горячие точки» — места первой встречи и борьбы за контроль карты. Задача состояла в том, чтобы изучить радары и навигацию реальных карт CS2 и улучшить геометрию подходов, мида и позиций возле плентов на оригинальных картах генератора.

## Что сделано

- `tools/fetch_radars.py` скачивает полный набор файлов радаров и метаданных из одной зафиксированной версии публичного каталога. В прошлой сессии проверены 74 изображения радаров и 24 файла метаданных. `handoff/radar-manifest.json` содержит ссылки и контрольные суммы. Каталог охватывает доступные в источнике материалы, включая отдельные этажи, варианты и служебные изображения. Выборка для замеров бралась из навов Dust II, Mirage, Inferno, Ancient, Cache и Tuscan в `data/nav/`.
- `src/14_taktika.js` ищет участки пола, куда T и CT при расчётном движении прибывают с разницей менее половины секунды. Прототип пробует продолжения существующих стен, когда получается слишком широкая полоса встречи. Варианты проверяются на связность и задержки на путях к ключевым точкам.
- `src/14_detali_profili.js` подключает прототип после сшивки проходов. В этом месте проверка проходимости учитывает высокие ящики и предметы. Встроенная статическая мера фронта при этом использует маску пола.
- Файлы `handoff/environment/` содержат установку и стартовые инструкции старой среды. Код сборки v142 в `builds/` остался исходным. Отдельные экспериментальные сборки лежат в `out/hotspots/` в архиве.

## Где остановились

Пользователь остановил работу над прототипом. Это снимок незавершённого эксперимента. Сохранились растры шести карт на тех же исходных параметрах до и после правки. Во встроенной модели максимальная зона стала меньше на пяти из шести карт. Для сида `4268400496` она изменилась с 213 504 до 35 840 кв. юнитов. Сопоставимый прогон финального экспорта, полный гейт и проверка в игре остаются открытыми. Файл `out/hotspots/changed/r.vmf` получен на более раннем варианте правки.

Модель описывает возможные встречи по времени подхода. Для оценки позиций обороны и реальных контактов ещё нужны высоты, линии обзора и разметка по демо либо проверка в игре. Фильтр ящиков в интеграции может удалить уже пересекающее стену укрытие даже на карте, где новый проход обработки не добавил стен. Это видно, например, по `removedCover` на сиде `4020866610`. В исходной v142 также есть известный провал гейта на маршрутах уже 96u.

## Как проверить после возобновления работы

Из корня репозитория с Node.js, Python 3 и браузером Playwright:

```bash
npm ci
npx playwright install chromium
python3 tools/fetch_radars.py
mkdir -p out/hotspots
node tools/sobrat.js out/hotspots/after.html
python3 tools/syncheck.py out/hotspots/after.html
node --check /tmp/build.js
node tools/rastr.js out/hotspots/after.html out/hotspots/repro 4268400496:4:123456
bash tools/priyomka.sh out/hotspots/after.html 3
```

Для сравнения с текущей правкой открывать `builds/izohrona_v142.html` и использовать ту же тройку `сид:цель:ковёр`. Изолировать тактический проход можно через `DETOFF=tactics` в `tools/rastr.js`. `out/hotspots/baseline/` и `out/hotspots/changed/` в архиве использовали другой сид укрытий, `193733861`. Скрипты из `research/` в архиве сохранены как черновики. У некоторых пути зашиты под `/workspace/izohrona`, а `frontier.py` и `vmf-front.py` требуют NumPy и SciPy.

Известных зависимостей от других чатов нет. Для восстановления среды достаточно выбрать `depthd/izohrona` и эту ветку. Прежние переменные браузера и кэша указывали на `/workspace/.cache/ms-playwright` и `/workspace/.cache/matplotlib`. Значения описаны в стартовых инструкциях.
